## Conflict resolutions

- **`common/common.cpp`**: upstream rewrote `fs_get_cache_directory()` with
  `std::filesystem` and a new `get_home_directory()` that calls `getpwuid()` on every
  non-Windows platform. wasi-sdk 25 has no `<pwd.h>`. Three `__wasi__` patches:
  - the `<pwd.h>` include is skipped on WASI;
  - `get_home_directory()` returns `/tmp` on WASI;
  - `fs_get_cache_directory()` keeps the fixed `/tmp/llama_cache` (same as before).
- **`common/common.h`**: upstream folded `use_mmap` / `use_mlock` / `use_direct_io`
  into one `enum llama_load_mode load_mode` (#20834). Its default
  `LLAMA_LOAD_MODE_AUTO` **enables mmap**, the IC0502 trap of Bug #3 in upgrade 0003.
  The patch now sets `load_mode = LLAMA_LOAD_MODE_NONE`. The `warmup = false` patch
  merged cleanly.
- **`common/log.cpp`**: upstream added `get_colors()` next to our `remove_file()`; both kept.
- **`ggml/src/ggml-backend.cpp`**: upstream added `alloc_buffer_n` and
  `get_alloc_size_n` to the CPU buffer type interface; our `get_max_size` cap is
  re-applied in the new layout. The split into a `multi_buffer` moved from
  `ggml_backend_alloc_ctx_tensors_from_buft_impl` to
  `ggml_backend_buft_alloc_buffer_n_default` / `_plan` but works the same way: buffers
  are planned by `get_max_size`, and a single larger tensor gets its own buffer.

## Upstream changes that needed canister changes

### Threadpool moved into `common_init_from_params` (#27026)

`tools/completion/completion.cpp` no longer creates a threadpool. `common_init_result`
now owns a `common_threadpools`, created and attached at context creation, and freed
after the context (`common/common.cpp`, `common_init_result::impl`).

In the canister `g_llama_init` owns that object, so the threadpool now lives exactly as
long as the persisted context. `src/main_.cpp` therefore no longer creates, attaches,
detaches or frees a per-call threadpool, and `CallTeardown` only frees the sampler and
log file. This removes the IC0502 dangling-threadpool class at its root (see
`README-0003-305ba519-IC0502.md`): there is no per-call pool left to dangle. The
mandatory IC0502 soak still has to confirm it (Gate 3).

### Version headers are generated by CMake

`ggml.c` includes `ggml-version.h` and `llama.cpp` includes `llama-version.h`, both
generated by CMake `configure_file()` from `*.h.in`. Upstream also switched to semantic
versions (`LLAMA_VERSION` 0.6.0, tags `v0.x` next to `bNNNNN`).

`scripts/version-headers.sh` fills in the templates with the values CMake would use
(`GGML_VERSION` 0.26.0, `LLAMA_VERSION` 0.6.0-dev, the fork commit). It runs as part of
`make build-info-cpp-{wasm,native}`, which every build path already calls (CI and
`scripts/build_wasm_docker.sh` included). The commit logic is shared with
`scripts/build-info-cpp.sh` through `scripts/fork-commit.sh`, so the three generated files
always agree. The two headers are git-ignored in the fork, like `common/build-info.cpp`.

### `llama_print_build_info` signature

Now `llama_print_build_info(const char * llama_version, FILE * stream)`;
`scripts/build-info-cpp.sh` emits the new form.

### `jinja/value.cpp` includes a bare `"unicode.h"`

It means `common/unicode.h`, but `src/unicode.h` (the tokenizer one) has the same name.
Upstream's CMake puts `common/` first; icpp-pro does not keep the include-dir order of
`icpp.toml` (the native build merges in the C include dirs). Fork patch: include
`"../unicode.h"`.

They were excluded "for the ICP globals limit (<1000)", a precaution taken in upgrade 0003
C3. The post-link globals fix brings the module to 1 defined global regardless, and it is
built into icpp-pro since 6.2.0. With the real code in, `src/wasi-chat-stubs.cpp` and
`src/wasi-speculative-stubs.cpp` are deleted.

**Behavior change:** `--grammar` / `--json-schema` used to trap (the stubs did that on
purpose, so a grammar request never ran unconstrained). With the real code linked, they
now constrain generation. The generation path still runs with `params.use_jinja = false`
and `LLAMA_ICP_NO_CHAT_TEMPLATES` (`src/main_.cpp`), so tokenization is unchanged.

Still excluded: `debug.cpp`, `llguidance.cpp`, `imatrix-loader.cpp`, `subproc.cpp`
(spawns processes), `download.cpp` + `hf-cache.cpp` (cpp-httplib), `console.cpp` (no TTY).

## Audits (canister-only bug classes, README-contributors-guide.md)

- **Class 1, catch-and-return APIs** in `llama-context.cpp`: the same 12 entry points as
  b10076, nothing new.
- **Class 2, `main_.cpp` re-port**: `completion.cpp` changed only in the threadpool block
  (above) and in using `llama_process(..., LLAMA_PROCESS_TYPE_ENCODE, ...)` for encoders.
  `llama_encode` / `llama_decode` / `llama_batch_get_one` still exist and are not
  deprecated, so `main_.cpp` keeps them. The verification greps all hit: `n_batch_ctx`
  x10, `embd.begin() + i` x3, the prompt-cache discard/stamp calls, and no
  `params.n_batch` in code.
- **Class 3, per-call registrations**: only the sampler and the log file remain, both
  torn down by `CallTeardown`. The threadpool is no longer per-call.
- **Prompt-cache layout stamp**: new `llama_cparams` fields are `n_outputs_max_per_seq`,
  `training` and `rope_scaling_type`. None shapes the KV / session-file layout for the
  generation path, so `state_layout_desc` is unchanged.
  **MISSED (fixed in v0.20.1):** the session serialization itself changed
  (`LLAMA_SESSION_VERSION` 9 -> 11), but `PROMPT_CACHE_FORMAT` stayed at v3. A canister
  upgraded from v0.19.1 kept its v0.19.1 prompt caches, the stamp vouched for them,
  `llama_state_load_file` rejected them on the version check, and every `run_update` on
  such a cache failed with `failed to load session file` until the cleanup timer removed
  it. Found by the Gate 4 A/B (v0.19.1 -> v0.20.0 on one canister). Fix: the stamp's
  format line now carries `LLAMA_SESSION_VERSION` / `LLAMA_STATE_SEQ_VERSION`
  (`prompt_cache_format()`, v4), so an upstream bump invalidates old caches automatically;
  regression test `native/test_prompt_cache_format.cpp`.
- **getenv**: new call sites go through `common_get_env()` /
  `common_get_path_from_env()`, which handle NULL (the canister's getenv override returns
  NULL). The new `ggml-cpu/tiled/tiled.cpp` reads `GGML_CPU_TILED_MM*` the same way.
