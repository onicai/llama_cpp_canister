# IC0502 `heap out of bounds` on the PERSISTED context (b10076 / 305ba519)

Post-mortem opened: 2026-09-17
Applies to: the b10076 (`305ba519`) line — v0.16.6 through v0.16.8 — as deployed
on the funnAI **prd** LLM fleet (Judge, ShareService, Challenger).
Related upgrade log: `README-0003-305ba519.md` (the b4531 → b10076 upgrade).
Work plan / handover: `TMP-HANDOVER-IC0502-graph-reuse.md`.

> The trap message reads `[TRAP]: heap out of bounds` (reject code IC0502).

## Outcome & reading guide (READ THIS FIRST)

**Status: ROOT CAUSE FOUND, FIXED, and reproduced+regressed locally
(2026-09-17).** It is a use-after-free write on a per-call threadpool, NOT the
graph-reuse hypothesis that headed the original analysis (graph reuse stays ON;
see below). The diagnostic body of this document is preserved as written; this
section records the resolution.

### Root cause: freed threadpool paused on the next call

Every update call creates a fresh ggml threadpool, attaches it to the persisted
`llama_context`, and frees it at end of call (`src/main_.cpp` teardown) WITHOUT
detaching. The freed pointer survives in two persisted places: `ctx->threadpool`
and the **CPU backend's own context**
(`ggml_backend_cpu_context::threadpool`, latched every compute by
`ggml_backend_cpu_set_threadpool`). On the next call's first compute, that
setter sees the new pool differs from the stale one and calls
`ggml_threadpool_pause(old)` on the **freed** block
(`ggml-cpu.c`, live because `GGML_USE_OPENMP` is off). The pool's `pthread`
mutex sits at offset 0 — exactly where dlmalloc keeps a free chunk's `fd`/`bk`
links — so the pause writes into freed heap and corrupts the allocator free
list. The trap then fires at a *later, unrelated* `malloc`/`free`, which is why
it presents as both Signature A (early in the next call, before any decode) and
Signature B (in the teardown frees) and why it is intermittent (it only bites
when the new pool lands at a different address than the freed one).

### Reproduction and regression

`test/test_ic0502_repro.py` replays the exact funnAI Judge/ShareService/
Challenger controller sequence (golden prd prompts) against one persisted
context. On the unfixed b10076 wasm it reproduced `[TRAP]: heap out of bounds`
in **cycle 0** (Signature B, `graphs reused = 73`), and every later call
re-trapped — matching prd. With the fix it runs **50 cycles (~1800 update
calls) clean**, `graphs reused` climbing past 2300 (graph reuse still ON).

### The fix (three layers, defense in depth)

1. `src/main_.cpp`: a `CallTeardown` scope-exit guard runs on every exit from
   `main_` (including the ~17 early returns that previously leaked). It calls
   `llama_detach_threadpool(ctx)` before freeing the pools, frees the sampler,
   closes the log file, and runs `reset_static_memory()`.
2. `llama-context.cpp` `detach_threadpool()`: also clears the copy latched in
   the persisted CPU backend (`ggml_backend_cpu_set_threadpool(backend_cpu,
   nullptr)`) — the copy that actually gets dereferenced.
3. `ggml-cpu.cpp` `ggml_backend_cpu_set_threadpool`: under `__wasi__`, skip the
   `ggml_threadpool_pause(old)` dereference entirely (single-threaded canister:
   pause is meaningless). Kills the UAF write even if a future path forgets to
   detach.

### Graph reuse: kept ON

The leading hypothesis in the diagnostic body below (cross-call graph reuse)
was NOT the cause. With the threadpool UAF fixed, the 50-cycle soak is clean
with graph reuse enabled, so it stays on and the b10076 speedup is preserved.
`can_reuse` still does not validate scheduler/buffer addresses, so the galloc
layer was hardened as a belt-and-braces guard (see the fix list below): a
cached tensor that would keep a data pointer into a freed/reallocated compute
buffer is now re-pointed instead of silently used.

### Other trap-class bugs fixed in the same pass

A full audit of the persisted-state class turned up more same-family bugs; the
trap-class ones were fixed here (wrong-output/cosmetic ones are backlogged, see
[Deferred backlog](#deferred-backlog)):

- **Prompt-cache stamp did not cover the context layout -> per-chat trap loop.**
  `llama_state_load_file`'s `try/catch` is dead under the WASI exception shim,
  so any cache it cannot parse throws -> traps -> re-traps forever. The stamp
  covered only the model, but the session-file byte layout also depends on the
  context (ctx-size, cache types, flash-attn, ...). A re-`load_model` with
  different context flags therefore left the old cache "valid" per the stamp
  and llama.cpp trapped on the layout mismatch -- reachable on every canister
  upgrade (the VFS persists, the loaded model does not, so it is re-loaded with
  whatever flags the new deploy uses). Fixed by stamping a context-layout
  descriptor (`llama_state_layout_desc`, `.icppfmt` line 3) and discarding on
  mismatch (stamp bumped v2->v3). A *torn* cache (a partial write) is not a
  concern on the IC: a trap rolls the whole message back, so a partial write to
  the VFS never commits.
- **`ready()` lied after a failed re-load / half-init unrecoverable.**
  `icpp_free_model()` now clears `ready_for_inference`, and `main_`'s reuse
  branch keys on `model == nullptr || ctx == nullptr` (was model only) and
  frees a half-initialized state before retrying.
- **17 early returns skipped teardown** (leaks + dangling static pointers) —
  closed by the `CallTeardown` guard above.

### Deferred backlog

Same-class findings that are wrong-output or cosmetic, not traps, left for a
follow-up: the `static bool defaults_cleared` DRY-sampler leak in
`common/arg.cpp`; UTF-8 tail-carry not cleared at 4 cache-deletion sites; the

garbage `total time` / `graphs reused` counters are cosmetic — IC time is
frozen within a message and the counters never reset); and rejecting `-bs`
(backend sampling) at the canister arg surface.

## Original leading hypothesis (SUPERSEDED — kept for the record)

**Status at the time: root cause LOCALIZED, not yet proven to a single
instruction.** Two distinct, perfectly reproducible trap signatures both land on
the code path that reuses the `llama_model` / `llama_context` persisted in
Orthogonal Persistence (OP) across update calls. This is a genuine bad memory
access on persisted state, which matches the earlier hand analysis ("the only
logical reason is a bad access of memory; everything else ruled out").

The **leading hypothesis** was ggml cross-call **graph reuse** (new in b10076):
the compute graph cached inside the persisted context is replayed on a later
call while something it references is no longer valid. (This turned out to be
NOT the cause — see the Outcome section above.)

What is NOT the cause (ruled out here and in prior work):
- **Not the prompt-cache discard.** A `Discarded prompt-cache … / Will create
  new` event is followed by a fully successful run at least as often as by a
  trap (see [ShareService LLM 3](#counterexample-a-discard-that-did-not-trap)).
- **Not `getenv`.** The `getenv`-fault class (README-0003 Bug #5) was fixed
  before v0.16.6 and its stub later removed once icpp-pro handled it. It plays
  no part here — though the dead `getenv` does matter for the FIX (below).
- **Not language / prompt content / `max_tokens`.** Traps hit English and
  Hindi, ingest and generate, on round token counts.

## How the logs were captured

Logging in the LLM canisters was turned on (`log_resume`) on 2026-09-17. The
funnAI monitor writes each canister's `dfx canister logs` to
`funnAI/scripts/logs-prd/SUBNET_*_*.log` (and `combined_logs.log`). The
pre-resume history is under `logs-prd/archive-pre-*`. These stdout logs are the
only signal available; there is **no** log file written *inside* the canister
(the controllers pass no `--log-file`, so `file_download_chunk` has nothing to
fetch — see [Why we can't go finer](#why-we-cant-go-finer-from-logs-alone)).

## The two trap signatures

Every trap is `[TRAP]: heap out of bounds`. In the current (post-resume) logs:

| Canister                        | Role        | Trap time (UTC) | Signature |
| ------------------------------- | ----------- | --------------- | --------- |
| `SUBNET_1_1_JUDGE_LLM_0`        | Judge 0     | 19:20:45        | A (in)    |
| `SUBNET_1_3_JUDGE_LLM_2`        | Judge 2     | 19:49:52        | A (in)    |
| `SUBNET_2_3_SHARE_SERVICE_LLM_2`| ShareSvc 2  | 19:41:18        | B (out)   |

The archives show this recurring for two days across Judge 0/1/2/3 and
ShareService 0/1/2/3 — many times per canister.

### Signature A — trap on the way IN (reuse of the persisted context)

The last line before the trap is always the model-reuse log:

```
main_: reusing the model & context loaded in a previous call
[TRAP]: heap out of bounds
```

That log is `src/main_.cpp:278` — the `else` branch where `g_model_persistent`
/ `g_ctx_persistent` are reused instead of freshly loaded. None of the
`LOG_INF` lines that come after it (`llama threadpool init`, `context batch
sizes = …`) ever appear, so the trap is inside the window between the reuse log
and the next surviving log point. In that window the code makes its **first
dereferences of the persisted context**:

```cpp
// src/main_.cpp (b10076 line numbers)
} else {
  LOG_INF("%s: reusing the model & context loaded in a previous call\n", ...); // 278
}
...
llama_memory_t mem = llama_get_memory(ctx);   // 309
llama_memory_clear(mem, true);                // 310  <-- first touch of reused KV
...
const llama_vocab *vocab = llama_model_get_vocab(model);          // 313
auto chat_templates = common_chat_templates_init(model, ...);     // 317
```

### Signature B — trap on the way OUT (teardown after a reused-graph run)

ShareService LLM 2 trapped 3× (18:48:12, 19:19:36, 19:41:18), each time on the
exact same line — the **last** line `common_perf_print` emits:

```
common_perf_print:    graphs reused =        200
[TRAP]: heap out of bounds
```

`common_perf_print` is `src/main_.cpp:1468`. The trap is therefore in the
teardown that immediately follows it:

```cpp
common_perf_print(ctx, smpl);          // 1468  <-- last output before trap
common_sampler_free(smpl);             // 1470
common_log_set_file(..., nullptr);     // 1474
reset_static_memory();                 // 1477
ggml_threadpool_free_fn(threadpool);       // 1484
ggml_threadpool_free_fn(threadpool_batch); // 1485
return 0;
```

Note `graphs reused = 200` is **identical** across all three ShareService traps,
and that same run reported nonsense timings (`total time = 16709799 ms`,
`unaccounted = 100.0 %`). The persisted context's own counters are already
garbage before the fault — a corrupt-reused-state tell.

### Counterexample: a discard that did NOT trap

ShareService LLM 3 at 20:06 discarded a stale cache, created a new one, then ran
to completion (`generate: n_ctx = 32768 …` → `main_: saving final output …` →
`common_perf_print`), no trap. This is why the cache discard is not the trigger.

## Diagnosis

Both signatures are the same root cause: **the `llama_context` (and its ggml
backend scheduler / compute-graph state) persisted in OP across update calls
holds a stale pointer that is dereferenced on a later call** — on the way in
(Signature A: `llama_memory_clear` on the reused context) or on the way out
(Signature B: freeing sampler/threadpool bound to a reused-graph run). "heap out
of bounds" is what the IC reports when that access lands outside the wasm heap.

This is consistent with the design note the code already carries at
`src/main_.cpp:377-392`: a size assumption on the persisted context (there,
`n_batch` vs the context's real batch) traps IC0502 and half-writes the caller's
prompt-cache. That whole class — "the persisted context is not what this call
assumes" — is the family this bug belongs to.

### Leading hypothesis: cross-call graph reuse

b10076 added compute-graph reuse to `llama-context`. The decision is at
`src/llama_cpp_onicai_fork/src/llama-context.cpp:1331`:

```cpp
if (!graph_reuse_disable && res->can_reuse(gparams)) {
    ...
    n_reused++;               // <-- "graphs reused = N"
} else {
    res->reset();
    ggml_backend_sched_reset(sched.get());
    ...
}
```

On the IC the context is the SAME object across calls (OP), so `gf_res_prev` /
the scheduler graph from the previous call survive and can be reused. If a later
call reuses a graph whose node→buffer / node→threadpool bindings are no longer
valid for this call's freshly created (and, at end of call, freed) threadpool
(`src/main_.cpp:365` create, `1484` free), the reused graph dereferences freed
or wrong memory → IC0502. The high, pinned `graphs reused = 200` on the
ShareService trap is what makes this the prime suspect.

**There is no runtime escape hatch.** Reuse is gated on
`graph_reuse_disable`, whose only setter is
`getenv("LLAMA_GRAPH_REUSE_DISABLE")` (`llama-context.cpp:274-276`). A canister
has no environment, so `getenv` returns `nullptr`, the flag keeps its
`false` default (`llama-context.h:379`), and **graph reuse is unconditionally ON
in prd**. Turning it off requires a code change, not a setting — which is the
first thing to try (see the handover).

This is a hypothesis, not proof. Signature A trapping *before* the first decode
of a call (i.e. before this call's graph work) means graph reuse may be only
part of the story, or the corruption is seeded on one call and detonates on the
next. The handover's instrumentation is what distinguishes these.

## Why we can't go finer from logs alone

- The surviving stdout is coarse: even healthy runs reliably emit only
  `generate: n_ctx = …` and the `common_perf_print` block. Most `LOG_INF` lines
  are absent and `LOG_DBG` never appears, so the trap dies *between* two
  surviving log points and stdout can name a code region, not a line.
- **Downloading an in-canister log file will not help as-is.** The controllers
  (`funnAI/PoAIW/src/Judge/src/Main.mo:1043`, etc.) pass no `--log-file`, so no
  file is written; and even with one it would carry the same coarse `LOG`
  stream. Finer detail needs added markers or a wasm backtrace — the handover.
